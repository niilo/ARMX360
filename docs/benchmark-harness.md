# On-device benchmark harness (`tools/bench-ab.sh`)

**Status:** tooling only. It changes no emulator behaviour and no cvar default. Its
job is to make performance claims **falsifiable** — to fail loudly when a run did
not actually test what it claims to test.

`docs/gw-gpu-bottleneck-investigation.md` §10 lists eight methodology traps, and
every one has already produced a *wrong* conclusion in this project's history.
None of that was a discipline failure: nothing forced the checks. This harness
turns each trap into an assertion.

## What it asserts, and where the strings come from

Every pattern the harness greps for was read out of the source. The important
ones, with citations:

| Log text | Source | What it proves |
|---|---|---|
| `----------- CONFIG DUMP -----------` … `----------- END OF CONFIG DUMP ----` | `config.cc:97`, `config.cc:119` | The global config file was read. Emitted by `PrintConfigToLog()` as **one** `XELOGI` with embedded newlines, so only the first physical line carries a log prefix. |
| `Loading game config: <path>` | `config.cc:335` | A per-game config was found and opened. **If this line is absent, no per-game override was applied** — `config.cc:329-331` returns early and silently when the file does not exist. |
| `  <name> = <value>` | `config.cc:350` | One line per key that was *actually applied*. Printed only for keys present in the file **and** matching a registered cvar. This is the strong assertion. |
| `Applied N game config override(s)` | `config.cc:354` | N = number of applied overrides. |
| `Loading custom Vulkan driver: <path>` | `ui/vulkan/vulkan_instance.cc` | Which driver library actually loaded. |
| `Custom Vulkan driver path '…' was set but the file does not exist; …` | `ui/vulkan/vulkan_instance.cc` | The run silently fell back to the **system** driver. Hard failure. |
| `Vulkan device '…': API …` / `* driverName: …` | `ui/vulkan/vulkan_device.cc` | GPU and ICD identity for the fallback case. |
| `Shader storage: pipeline file … (N bytes on disk)` | `gpu/shader_storage.h:237` | `0 bytes` ⇒ **cold** pipeline cache ⇒ discard the run (trap 1). |
| `Loaded N pipeline descriptions, M shader translations needed` | `gpu/shader_storage.h:422` | How much shader translation work the run did. |
| `Set TU_PERF_SAMPLER=… for the Turnip driver` | `ui/vulkan/vulkan_instance.cc` | The **instrumented** Turnip build. `report` refuses to emit fps from such a run. |

Log lines are prefixed `"<type>> f:<frame:07> <thread id:08X> "` (`base/logging.cc`)
— a guest frame counter, **not** a clock. The harness strips that prefix from
every physical line before matching, which is what makes the multi-line CONFIG
DUMP greppable at all.

### Two things the log does *not* contain

- **No fps.** The overlay's fps lives in process-local atomics
  (`base/frame_stats.h`) reachable only via JNI. The harness samples fps from the
  compositor instead: `adb shell dumpsys SurfaceFlinger --latency '<layer>'`,
  whose rows are `<desiredPresent> <actualPresent> <frameReady>` in nanoseconds.
  The gap between consecutive `actualPresent` values is a true present-to-present
  interval.
- **No wall-clock timestamp.** The harness cannot time anything from `xe.log`.

### Per-game config path (checked before *and* after)

`GetGameConfigPath()` (`config.cc:50`) builds
`<config_folder>/config/<TITLEID>.config.toml`, where `config_folder` is the
`--storage_root` the app passes (`EmulatorHostActivity.kt` →
`Utils.get_storage_root_path()` → `Application.get_app_data_dir()`), i.e. on this
fork:

```
/sdcard/Android/data/<package>/files/compose/config/<TITLEID>.config.toml
```

Keys are looked up as `category.name` (`config.cc:340-341`), so the section header
is required — see `GAME_COMPAT.md`. `snapshot-config` records size + sha256 before
the run; `verify-config` re-checks after. This is trap 3: GW's config was once
deleted mid-session, silently reverting `readback_resolve` and looking like a
broken build.

## Usage

```sh
# 0. Host preflight: catches STALE GENERATED BYTECODE (trap 5) before you build.
tools/bench-ab.sh preflight

# 1. Record the free variables (trap 8: the driver is a free variable).
tools/bench-ab.sh device-info > device-info.txt

# 2. Pin the config: record the per-game file's identity BEFORE the run (trap 3).
tools/bench-ab.sh snapshot-config --title-id 584108FF --out before.txt

# 3. Launch the game yourself, then sample. Run it TWICE and keep the second:
#    the first run after a new build recompiles pipelines and reads fps low.
tools/bench-ab.sh sample --label armA --samples 3 --seconds 20 --out samples.csv

# 4. Verify the per-game config survived the run (trap 3, again).
tools/bench-ab.sh verify-config --title-id 584108FF \
    --before "$(awk '{print $3}' before.txt)"

# 5. Assert every intended cvar actually applied, and that the right driver ran.
adb pull /sdcard/Android/data/armx360.compose/files/compose/xe.log xe.log
tools/bench-ab.sh assert-log --log xe.log \
    --expect game.readback_resolve=none \
    --expect game.render_area_dirty_extent=true \
    --expect global.vulkan_mid_frame_submission_draws=1300 \
    --driver-path mainline-turnip-V31

# 6. Report, then compare arms.
tools/bench-ab.sh report --log xe.log --label armA samples.csv
tools/bench-ab.sh compare armA.csv.report armB.csv.report
```

`--expect game.NAME` vs `--expect global.NAME` is **not** cosmetic. The two prove
different things: `game.*` matches the per-game override block (strong — the line
only exists for keys that reached a live cvar), while `global.*` matches the CONFIG
DUMP (weaker — it reflects the file's text, so a later per-game override could
still win). An unqualified `--expect` is rejected rather than guessed.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | Ran; all assertions held. |
| 1 | An assertion failed — **the measurement is void**. |
| 2 | Bad invocation. |
| 3 | **Refused to report**: instrumented driver, cold pipeline cache, or too few samples to estimate noise. |

Code 3 exists so a "no result" is distinguishable from a "failed result". It is
the harness refusing to print a number, not an error.

## Noise, and what counts as a real difference

Trap 7: readings carry ~±2fps, and a neutral commit was once **reverted** on the
strength of a 13-vs-15 reading. So `compare` computes

```
se = sqrt(sd_a²/n_a + sd_b²/n_b)
```

and reports `verdict=REAL` only when `|Δfps| > 2·se`; otherwise
`verdict=WITHIN_NOISE`. With n=3 per arm and sd≈2fps that is a ≈±2.7fps band —
deliberately conservative, because under-reading a real win costs less than
inventing one. Fewer than 3 samples per arm is refused outright: one reading has
no noise estimate at all.

## Normalising for activity

Runs differ by ~5% in in-game activity, which moves raw fps without any code
change. §12.7 normalised per shaded pixel to cancel it.

**That normalisation needs the counter sampler, which only exists on the
instrumented Turnip build — and instrumented runs must never be used for fps
claims (§3, §12.5).** There is no shaded-pixel counter on a production driver, so
the harness deliberately does **not** fake one. It reports raw fps with its noise
band and refuses to normalise, because:

- `VkPassTime`'s per-bucket `WxH` area is **declared** area, not work — §5.2's
  correction and §12.7 both established that a build with fewer declared pixels
  measured the *same*, so normalising by it would cancel a quantity unrelated to
  cost.
- `draws/frame` (available from `VkFrameSync` with
  `log_gpu_frame_time_breakdown`) is a legitimate activity proxy but is a
  different metric, not shaded pixels.

If you want true per-shaded-pixel normalisation, do it on the counters, on both
arms, with the sampler enabled — and report it as a **counter** result, keeping
the fps claim from the production-driver run.

## Testing the harness itself

A checker that never fails is worse than no checker. `tools/bench-ab-test.sh` runs
offline (no device, no adb) and **fails if any assertion does not fire**:

```sh
tools/bench-ab-test.sh     # 36 checks
```

Fixtures in `tools/testdata/bench-ab/` are hand-written from the source format
described above, and each negative fixture is engineered to break exactly one
assertion:

| Fixture | Must fail because |
|---|---|
| `missing-cvar-xe.log` | A per-game cvar was never applied (trap 2) |
| `wrong-value-xe.log` | The cvar applied, but with the global value (trap 2) |
| `no-game-config-xe.log` | No per-game config at all — the trap-3 signature (trap 3) |
| `cold-cache-xe.log` | `0 bytes on disk` pipeline cache (trap 1) |
| `instrumented-xe.log` | Instrumented driver, and driver ≠ pin (trap 8) |
| `driver-missing-xe.log` | Configured driver path missing → silent system fallback (trap 8) |

If the emulator's log format changes, these fixtures **must** be updated alongside
the assertions — that coupling is deliberate.

## What has and has not been verified

Verified by execution:

- `bash -n` on both scripts; `--help`; unknown-command exit code 2.
- All 36 suite checks, including every negative case above.
- Against a **real attached device** (Pocket S, Android 13, Adreno, `qcom`):
  `device-info`, `preflight`, `snapshot-config`, and the full trap-3 round trip —
  file untouched → pass; config silently rewritten → fail; config deleted → fail.
  Device `sha256sum` and `stat -c %s` both work, so the identity check is sound.
- `dumpsys SurfaceFlinger --latency` parsing, against a live SurfaceView layer.
- `assert-log` against a **real captured log** (5,120,152 bytes / 64,493 lines,
  pulled byte-count-identical from the release package): the `Shader storage:
  pipeline file ... (N bytes on disk)` format, the `Loaded N shaders from
  storage` / `Loaded N pipeline descriptions, M shader translations needed` pair,
  the `CONFIG DUMP` markers, and `Loading custom Vulkan driver: <path>` all match
  the fixtures' shape, so the extractor and its `strip_prefix` are sound.
  `--driver-path` matched a real driver path out of that log.

### Fixtures reconciled against a real log — one invented number

`docs/benchmark-harness.md` previously said the fixtures were reconstructed from
source and should be checked against a real run. That check is now done, and it
found a fabricated value: every warm fixture claimed
`(9186 bytes on disk)`, a number with no source behind it. A real warm cache
reports **`15390`**, on every one of the log's four sessions. Fixtures and the
suite's `expect_output "cache.bytes=..."` now both say 15390, with the
coupling called out at the assertion — editing one without the other fails a
check, which is the behaviour you want.

Two other drifts are worth knowing and are **not** fixed, because they would
change what a stock install runs:

- `vulkan_async_skip_draws` ships `true` in `default_config.toml` while
  `DEFINE_bool` says `false`; `vulkan_log_debug_messages` ships `false` while
  `DEFINE_bool` says `true`. The template wins at runtime, so the settings screen
  already agrees with reality and there is no live bug — but the C++ default is
  misleading to anyone reading it. Same class of drift as
  `docs/a830-gmem-msaa-plan.md`'s corrected `vulkan_in_pass_resolve` entry, which
  *was* user-visible (the template omits that key) and is now asserted by
  `SettingsSchemaTest.bool_defaults_match_effective_native_default`.
- The real log contains **no** `VkFrameSync`, `VkPassTime` or `fps` line, so
  `instrumented-xe.log`'s two such lines are impossible-in-reality. Harmless —
  that fixture exists to trip the instrumented-driver gate, which keys on the
  driver marker, not on those lines — but they are aspirational, not captured.

**Not** verified here, and needing a real measurement setup:

- A full game run end to end (launch → sample → assert → report). No title was
  installed and no emulator session was run, so **no fps number in this repository
  comes from this harness yet**, and none is claimed.
- `preflight`'s bytecode-generation branch needs `glslangValidator`, `spirv-opt`
  and `spirv-dis`; they are absent from this environment, so only the
  missing-tool warning path was exercised.

### Trap 9 — a cvar the binary does not have fails *silently*

This is new, and it is the nastiest member of the family, because the harness
cannot catch it: `config.cc:338-345` resolves per-game keys only against
pre-registered `cvar::ConfigVars`. A key the installed binary never registered is
not a cvar, is not an error, and logs nothing. Setting `log_gpu_pass_break_reasons`
in a per-game file against a **release** build therefore looks identical to
success — no warning, no `Applied` line for it, and `assert-log` reporting
`assert.failures=0` for the cvars it *can* see.

Verified by pulling both installed APKs and grepping `lib/arm64-v8a/libe.so`:

| string | release | debug |
|---|---|---|
| `VkPassBreaks` | 0 | 2 |
| `VkPassSplit` | 0 | 3 |
| `log_gpu_pass_break_reasons` | 0 | 1 |
| `gpu_idle_stall_backoff_ms` | 0 | 2 |
| `vulkan_hdr_render_target_as_b10g11r11` | 0 | 1 |

So the pass-count instrumentation is **only in the debug build**, and a
measurement aimed at the release package will silently produce a log with no
pass data. The fix belongs in `preflight`: it already records the commit and
warns on a dirty tree, so it can also refuse a `--driver-path`-style package
whose binary lacks the cvar being measured. Until then, grep the APK:

```sh
unzip -p <apk> lib/arm64-v8a/libe.so | strings | grep -c '^log_gpu_pass_break_reasons$'
```

## One unattended-run caveat

`am start -n armx360.compose.debug/xendroid.compose.EmulatorHostActivity -a
xendroid.intent.action.xendroid --es game_uri <iso>` boots with no tap — the
activity is `exported="true"` and boots from `surfaceCreated`
(`EmulatorHostActivity.kt:449-471`). But on a device whose display is not being
watched, a persistent `NotificationShade` window can hold `mCurrentFocus`
indefinitely: the activity stays in `mLastPausedActivity` with `isOnScreen=false`,
so no surface is created, `bootOnce()` never runs, no frame is ever rendered, and
`assert-log` sees a log with zero `VkPassTime`/`VkFrameSync` lines. It survived
`cmd statusbar collapse` and a SystemUI restart. Granting All Files Access is
also required for the boot to get past
`EmulatorHostActivity.kt:179-185`, which checks
`Environment.isExternalStorageManager()` at runtime — so the process must be
started *after* the grant, or it will `finish()` on the old cached value.

## 3. What was established this session

### 3.1 The study's central claim was wrong, and is corrected

`docs/x360-arch-emulation-study.md` §5 said "no frame ever rendered on the
attached device". Re-derivation from the captured logs refuted it: the guest
issued **~33,000 frontbuffer swaps**. The log-prefix frame counter is advanced
only in the `PM4_XE_SWAP` handler (`pm4_command_processor_implement.h:815`), so a
climbing counter means that many guest presents. The four tokens the old claim
rested on were all vacuous — two gated behind `log_gpu_frame_time_breakdown`
which was `false`, one behind `debug_markers_enabled()`, and `DrawCallBegin`
**is not a string this codebase can emit** (0 files).

`MemoryPollPark` was additionally wrong in kind: it is a **translation-time
compiler pass** (`memory_poll_park_pass.cc:219`), so 1595 lines means 1595 poll
loops *compiled*, not 1595 runtime parks.

Committed as `237af848d`. §7 was reordered as a consequence.

### 3.2 The HID hotplug loop — new instrumentation, and cross-build corroboration

`UpdateUsedSlot` is reached from `GetStateForUI`, the guest's **per-frame query
path**, so a slot's connected state is decided by "did this individual poll
succeed" rather than "is a device present". `GetStateForUI` answers success only
when `(flags & driver->GetInputType()) != 0`, and `InputType::Controller` is 1
(`input_driver.h:33`) while `X_INPUT_FLAG_GAMEPAD` is 1 (`input.h:32`) — they
agree only by numeric coincidence. `X_INPUT_FLAG_ANY_USER` is `1 << 30`
(`input.h:38`), bit 0 clear, and `xam_input.cc:119` explicitly expects guests to
send it.

Every flip logs and broadcasts `kXNotificationSystemInputDevicesChanged` under
the kernel global lock. The guest did register a listener
(`XamNotifyCreateListener` in the captured log).

**Mechanism still unverified.** The instrumentation exists to settle it and has
never run. Hypothesis: a bucket with `err == polls` names the guilty flag value.

Corroboration across binaries (the churn log lines are old code, so they show on
an un-instrumented build):

| build | title | frames | churn lines | shape |
|---|---|---|---|---|
| debug, 10-04 | SSX | 22,163 | 32,797 | `F8000008` 28,510 connects / 0 disconnects; `F8000170` 22,604 + `F800016C` 10,191 disconnects |
| release, 10-09 | SSX | 4,541 | 4,541 | `F8000168` 4,540 disconnects + 2,601 connects; `F8000008` 1,940 connects / 0 disconnects |
| debug, 10-09 | Gears `4D53082D` | 13,983 | **1** | none |

One thread connects exclusively, another disconnects exclusively, on two
different binaries and two different boots. **The churn is title-specific** —
Gears does not exhibit it.

**The stall hypothesis is refuted.** Gears hit the
`GuestScheduler: no guest frame presented` watchdog 3× with essentially zero
churn, so churn is **not necessary** for the stalls. Causation was previously
"unproven"; it is now dead. The stalls have another cause, unknown.

### 5c. The actual cause: a crash in the instrumentation itself

Re-running on 2026-10-09 with the screen held awake found it. The process is not
stalling — it is **dying**, and it has been dying since the instrumentation landed:

```
E libc++abi: terminating due to uncaught exception of type
  fmt::v12::format_error: invalid format specifier
F libc    : Fatal signal 6 (SIGABRT) in tid 29325 (GPU Commands (0))
```

Symbolized against the exact installed binary (Build ID
`d03a6b8f5ec3ab2b34d6488b81372ef98430a09e`, matched against
`emulator-core/build/intermediates/cxx/RelWithDebInfo/426b6d25/obj/arm64-v8a/libe.so`):

```
logging.h:198  XELOGI
vulkan_presenter.cc:2266            <-- the throw
presenter.cc:1307                  PaintAndPresent
presenter.cc:458                   RefreshGuestOutput
vulkan_command_processor.cc:2435    IssueSwap
pm4_command_processor_implement.h:811   IssueSwap call site
```

**The defect.** `vulkan_presenter.cc:2267` formats `present_cost_frames_` — a
`uint64_t` (`vulkan_presenter.h:502`) — with `{:.0f}`, a float presentation type.
fmt rejects that pairing and throws. Every *other* argument on that line is
explicitly `static_cast<double>(...)`; this one was missed. Introduced by
`4cf30a60f`, which has never once printed a line on device.

**Why it presented as "frame 0".** This is the part that made it look like a stall.
The throw happens *inside* `IssueSwap`, and the log-prefix frame counter is
advanced at `pm4_command_processor_implement.h:815` — **after** the `IssueSwap` call
at `:811`. So the counter can never advance past 0 when this fires. The `f:` column
is not evidence of an absent present; it is evidence of a present that died
mid-call. Frame 0 was the *symptom*, and §5 read it as the disease.

**Why the release build is unaffected.** It has zero occurrences of
`log_present_path_cost` in its `libe.so` (§4), so the throwing line is not compiled
into it. That asymmetry — release presents, debug dies — is fully explained, and it
is the instrumentation's own log statement, not the instrumented behaviour.

**Also established: the guest does present on the debug build.** The report only
fires when `present_cost_frames_` is non-zero (`vulkan_presenter.cc:2260`), and that
counter is only incremented under `cvars::log_present_path_cost &&
guest_output_flow.effect_count` (`:1648-1655`). So the crash proves at least one
frame with a non-empty guest output flow was painted. The claim that debug never
presents is false.

```
VkPresentCost: 30 frames, 1.0 passes/fr, present=3.69Mpx/fr
               guest=0.92Mpx/fr ratio=4.00x swapchain=2560x1440
```

**`ratio=4.00x`, sustained across 86 consecutive reports**, with the guest at
0.92 Mpx/frame and the present path at 3.69 Mpx/frame. 0.92 Mpx = 1280×720, so the
guest is unchanged and the **entire** 4× is the present path. This confirms the
study's §4.1 overdraw claim as a measurement rather than an inference, and it is
the first `VkPresentCost` line ever printed on any build.

Read it as a **floor**, as the code comment says (`vulkan_presenter.cc:1642-1647`):
it counts pixels, not the per-pixel cost of whichever shader each pass runs. And
`passes/fr = 1.0` means the present path is a **single full-screen quad** — so this
is one overdraw, not N. Whether that quad's per-pixel shader cost dominates is
still unmeasured; that is the `VkPassSplit` question, and §5f below explains why it
cannot be asked yet.

Also verified in the same run: `f:` climbed to **2,532** (vs 0 on every previous
debug run), and **no SIGABRT** in logcat.

### 5e. `HidPoll` answers §3.2's open question: flags `0x8`

The handover recorded the hypothesis as *"a bucket with `err == polls` names the
guilty flag value"* and said the instrumentation had never run to test it. It has
now run, and the answer is unambiguous. Across 774 `HidPoll` lines:

| slot | flags | polls | err | verdict |
|---|---|---|---|---|
| 0 | `0x1` | 30 | **0** | the only answered poll |
| 0 | `0x8` | 30 | **30** | every poll fails |
| 1–3 | `0x1` | 30 | **30** | every poll fails |
| 1–3 | `0x8` | 30 | **30** | every poll fails |

**`0x8` is `X_INPUT_FLAG_UNKNOWN2`** (`input.h:35`) — not `GAMEPAD` (0x1), not
`KEYBOARD` (0x2), and not `ANY_USER` (`1 << 30`, which §3.2 correctly predicted
would arrive). `GetStateForUI` answers success only when
`(flags & binding.driver->GetInputType()) != 0` (`input_system.cc:316`), and
`InputType::Controller` is **1** (`input_driver.h:33`) — so **`0x8 & 1 == 0`, always.**
Every `0x8` poll takes the failure branch to `UpdateUsedSlot(nullptr, user_index,
false)` (`:333`), i.e. a *disconnect*, on every frame. The churn is a flags-enum
mismatch, not a device-presence question: the guest asks for a class of device the
driver's type bit cannot express.

Slot 0 / `0x1` succeeding is consistent — that is the one combination where the bits
do overlap. Note the `err` asymmetry is *not* about slots 1–3 lacking controllers;
it is entirely a function of the flags value.

**Replicated on the confirmation run** (boot 3, aggregated over all 88 reports, so
the per-bucket counts are exact rather than per-second samples):

| flags | slot 0 | slot 1 | slot 2 | slot 3 |
|---|---|---|---|---|
| `0x1` | 2,586 polls / **0 err** | 2,585 / **2,585** | 2,585 / **2,585** | 2,585 / **2,585** |
| `0x8` | 2,585 / **2,585** | 2,585 / **2,585** | 2,585 / **2,585** | 2,585 / **2,585** |

Totals: `0x8` = 10,340 polls, 10,340 errors — **`err == polls` exactly, to the
poll**. And `0x1` = 10,341 polls / 7,755 errors, where the 7,755 are precisely the
three non-zero slots. The perfectly uniform per-slot counts are the signature of a
per-frame poll loop: one poll per slot per frame, ~2,585 frames, no variance.

**Still unverified:** whether SSX is *supposed* to send `0x8` (guest bug, or an
enum this codebase mis-transcribes), and what the correct behaviour should be. What
is now measured is the mechanism, which was the open question.

### 5f. Second defect found in the same pass: `VkOverhead` is unreachable as configured

`VkOverhead` (`vulkan_command_processor.cc:2398`) and `VkPassSplit` (`:2355`) are
**nested inside `if (cvars::log_gpu_frame_time_breakdown)`** at `:2271`, verified by
brace-depth trace — both sit under three enclosing blocks ending in that gate. So
`log_gpu_pass_break_reasons = true` **alone prints nothing.** The per-game config in

`log_gpu_frame_time_breakdown`, so as written it cannot produce the `VkOverhead`
line it exists to produce. That is trap 9's failure mode arriving through a gate
rather than a missing binary: no data, no warning.

**Not fixed, deliberately.** Hoisting the block changes gating semantics and would
mean shipping an unmeasured change; the decision belongs with whoever runs the
measurement. Recorded so the next person does not read a silent `VkOverhead` as a
zero.

## 6. Build trap that cost an install

The first `adb install -r` failed with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.

**The container generates a fresh debug keystore on every run.** Only
`/root/.gradle` is persisted, so `/root/.android/debug.keystore` is created fresh
and discarded, and every build gets a different signature.

Fix — seed the container with a *copy*, leaving the real keystore untouched:

```sh
mkdir -p /tmp/opencode/android-seed
cp ~/.android/debug.keystore /tmp/opencode/android-seed/
docker run --rm -v "$PWD":/src -v armx360-gradle-cache:/root/.gradle \
    -v /tmp/opencode/android-seed:/root/.android armx360-build ./gradlew :app:assembleDebug
```

Verify before installing — this is cheap and catches the whole class:

```sh
apksigner verify --print-certs app-debug.apk | grep 'SHA-256 digest'
```

## 9. Rules that were nearly broken this session

- **Trap 9.** Verified three times: the installed release build has **zero**
  occurrences of every new counter. A release run yields no data and no
  complaint. Always grep the APK before trusting a run.
- **A zero count proves nothing.** §5's original error was reading absent
  `VkPassTime` lines as "nothing rendered" when the cvar was simply off.
- **Per-game config files vanish silently** and a title-ID mismatch is also
  silent. Verify before *and* after every run.
- **`grep -n` without `-E`** treats `(dis)?` literally and silently returns 0
  matches — it briefly reported "0 controller lines" for a log that had 32,797.
- **`sort -n` eats leading zeros**, so `f:0022163` sorted as 22163 and I
  under-counted a frame total by 10×. Strip leading zeros before sorting, or
  `printf '%d'`.

Added on the second 2026-10-09 pass, after re-deriving §5:

- **Check the end of the log before naming a failure mode.** "0 swapchains" and
  "stalls at the surface" were both read off the *middle* of a log whose last line
  is a clean `Saved … VkPipelineCache` shutdown at `uptime_ms=3180`. The stop happened
  before any fault could show. Read the tail, and read `uptime_ms`, before
  characterising anything as a hang.
- **"Gated off by default" does not exonerate a cvar in a run that enabled it.**
  All three counters were set on this run by the per-game config. The exoneration
  and a symmetric accusation are both unsupported; the correct word is untested.
- **Absence of a counter line is not evidence about the thing it would measure.**
  `HidPoll` / `VkPresentCost` cannot appear in a run that never presents. That is
  circular, and it is the same mistake §5 of the study already made once with
  `VkPassTime`.
- **`f:0` does not mean "did not present".** It means
  `logging::IncrementFrameNumber()` did not run — which is also what happens when
  `IssueSwap` aborts first, since the increment is at
  `pm4_command_processor_implement.h:815`, *after* the `IssueSwap` call at `:811`.
  A crash between those two lines is indistinguishable from a stall if you read only
  the frame column. This is the mistake that produced §5's wrong reading.
- **Check logcat for a crash before reading a stall into `xe.log`.** `xe.log` has no
  crash line and no `FATAL SIGNAL`; the abort appears only in logcat, as
  `libc++abi: terminating due to uncaught exception` and
  `Fatal signal 6 (SIGABRT)`. The `xe.log` tail looks identical either way.
- **Symbolize against the installed binary's Build ID, not a random `libe.so`.**
  Several `libe.so` copies sit under `app/build/` and `emulator-core/build/`; only
  the `RelWithDebInfo/426b6d25` one matches the shipped
  `d03a6b8f5ec3ab2b34d6488b81372ef98430a09e`. `readelf -n` each candidate and compare
  before trusting a backtrace — a mismatched one produces confident nonsense.

## 3. What was established this session

### 3.1 The study's central claim was wrong, and is corrected

`docs/x360-arch-emulation-study.md` §5 said "no frame ever rendered on the
attached device". Re-derivation from the captured logs refuted it: the guest
issued **~33,000 frontbuffer swaps**. The log-prefix frame counter is advanced
only in the `PM4_XE_SWAP` handler (`pm4_command_processor_implement.h:815`), so a
climbing counter means that many guest presents. The four tokens the old claim
rested on were all vacuous — two gated behind `log_gpu_frame_time_breakdown`
which was `false`, one behind `debug_markers_enabled()`, and `DrawCallBegin`
**is not a string this codebase can emit** (0 files).

`MemoryPollPark` was additionally wrong in kind: it is a **translation-time
compiler pass** (`memory_poll_park_pass.cc:219`), so 1595 lines means 1595 poll
loops *compiled*, not 1595 runtime parks.

Committed as `237af848d`. §7 was reordered as a consequence.

### 3.2 The HID hotplug loop — new instrumentation, and cross-build corroboration

`UpdateUsedSlot` is reached from `GetStateForUI`, the guest's **per-frame query
path**, so a slot's connected state is decided by "did this individual poll
succeed" rather than "is a device present". `GetStateForUI` answers success only
when `(flags & driver->GetInputType()) != 0`, and `InputType::Controller` is 1
(`input_driver.h:33`) while `X_INPUT_FLAG_GAMEPAD` is 1 (`input.h:32`) — they
agree only by numeric coincidence. `X_INPUT_FLAG_ANY_USER` is `1 << 30`
(`input.h:38`), bit 0 clear, and `xam_input.cc:119` explicitly expects guests to
send it.

Every flip logs and broadcasts `kXNotificationSystemInputDevicesChanged` under
the kernel global lock. The guest did register a listener
(`XamNotifyCreateListener` in the captured log).

**Mechanism still unverified.** The instrumentation exists to settle it and has
never run. Hypothesis: a bucket with `err == polls` names the guilty flag value.

Corroboration across binaries (the churn log lines are old code, so they show on
an un-instrumented build):

| build | title | frames | churn lines | shape |
|---|---|---|---|---|
| debug, 10-04 | SSX | 22,163 | 32,797 | `F8000008` 28,510 connects / 0 disconnects; `F8000170` 22,604 + `F800016C` 10,191 disconnects |
| release, 10-09 | SSX | 4,541 | 4,541 | `F8000168` 4,540 disconnects + 2,601 connects; `F8000008` 1,940 connects / 0 disconnects |
| debug, 10-09 | Gears `4D53082D` | 13,983 | **1** | none |

One thread connects exclusively, another disconnects exclusively, on two
different binaries and two different boots. **The churn is title-specific** —
Gears does not exhibit it.

**The stall hypothesis is refuted.** Gears hit the
`GuestScheduler: no guest frame presented` watchdog 3× with essentially zero
churn, so churn is **not necessary** for the stalls. Causation was previously
"unproven"; it is now dead. The stalls have another cause, unknown.

### 3.3 Two further defects found, neither fixed

- `xam_input.cc:116-122` computes `actual_user_index`, pins it to 0, then passes
  `user_index` at `:128`. The variable is unused, and the guard at `:106` already
  rejects `XUserIndexAny` before the pinning can matter, so the block is
  unreachable as written.
- `KernelState::GetConnectedUsers` (`kernel_state.cc:1303-1309`) takes the input
  lock and has **no callers**. So the apparent ABBA against
  `BroadcastNotification`'s `global_critical_region_` is **not** realised. Refuted
  deliberately — recorded so it is not re-investigated.

## 4. Why no counters yet

Both blockers were hit, in this order:

1. **Title-ID mismatch.** The per-game config was written for `4541096D` (from
   the captured 10-04 log) but the run booted Gears `4D53082D`.
   `config.cc:329-331` returns early and logs **nothing** when the file does not
   match. Silent — no warning, no error.
2. **Release build has no instrumentation.** `armx360.compose` is `0f10fd3`,
   seven commits behind. Verified in its `libe.so`: `log_present_path_cost` **0**,
   `VkPresentCost` **0**, `VkOverhead` **0**, `log_input_poll_breakdown` **0**,
   `HidPoll` **0**. It also has no `config/` directory at all.

**The per-game config mechanism is proven working.** On the debug SSX launch:

```
Loading game config: .../4541096D.config.toml
  log_gpu_pass_break_reasons = true
  log_input_poll_breakdown = true
  log_present_path_cost = true
Applied 3 game config override(s)
```

`Applied N game config override(s)` is the check to look for. **Not** the CONFIG
DUMP: `log_present_path_cost` and `log_input_poll_breakdown` do not appear there
even when registered, because the dump reflects the global config as it was at
boot and the app only rewrites that file afterwards.

## 6. Build trap that cost an install

The first `adb install -r` failed with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.

**The container generates a fresh debug keystore on every run.** Only
`/root/.gradle` is persisted, so `/root/.android/debug.keystore` is created fresh
and discarded, and every build gets a different signature.

Fix — seed the container with a *copy*, leaving the real keystore untouched:

```sh
mkdir -p /tmp/opencode/android-seed
cp ~/.android/debug.keystore /tmp/opencode/android-seed/
docker run --rm -v "$PWD":/src -v armx360-gradle-cache:/root/.gradle \
    -v /tmp/opencode/android-seed:/root/.android armx360-build ./gradlew :app:assembleDebug
```

Verify before installing — this is cheap and catches the whole class:

```sh
apksigner verify --print-certs app-debug.apk | grep 'SHA-256 digest'
```

## 9. Rules that were nearly broken this session

- **Trap 9.** Verified three times: the installed release build has **zero**
  occurrences of every new counter. A release run yields no data and no
  complaint. Always grep the APK before trusting a run.
- **A zero count proves nothing.** §5's original error was reading absent
  `VkPassTime` lines as "nothing rendered" when the cvar was simply off.
- **Per-game config files vanish silently** and a title-ID mismatch is also
  silent. Verify before *and* after every run.
- **`grep -n` without `-E`** treats `(dis)?` literally and silently returns 0
  matches — it briefly reported "0 controller lines" for a log that had 32,797.
- **`sort -n` eats leading zeros**, so `f:0022163` sorted as 22163 and I
  under-counted a frame total by 10×. Strip leading zeros before sorting, or
  `printf '%d'`.
